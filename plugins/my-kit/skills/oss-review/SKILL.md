# 오픈소스 도입 검토 리포트

입력은 검토 주제이고, 저장소(owner/repo)는 선택입니다. 주제가 없으면 사용자에게 먼저 묻습니다. 조회일은 오늘 날짜(YYYY-MM-DD)를 씁니다.

## 저장소 정하기
저장소가 주어지면 그대로 씁니다. 없으면 아래 순서로 후보를 찾습니다. 1번은 직접 하고, 2번과 3번은 my-kit:mcp-researcher 에이전트에게 맡깁니다.
1. 지식 후보: 검토 주제에 맞는 공개 저장소를 모델 지식으로 2~3개 고릅니다. 최근 논문의 공식 구현처럼 새로 나온 저장소도 포함합니다.
2. 허브 탐색: 주제의 대표 저장소 1~2개를 허브로 정하고, 위키 질의 도구로 이 저장소가 통합하거나 의존하거나 대안으로 언급하는 관련 저장소(owner/repo)를 묻습니다. 예를 들어 프롬프트 최적화라면 DSPy 같은 대표 저장소에 연동된 최적화 엔진 저장소를 묻습니다. 사용자가 허브를 적어 주면 그 저장소를 허브로 씁니다.
3. 확인: 1과 2에서 나온 후보를 위키 목차 조회 도구로 하나씩 확인하고, 확인된 것만 남깁니다.
4. 제시: 남은 후보를 최대 5개까지 표로 보여 줍니다. 칸은 저장소, 한 줄 설명, 찾은 경로(지식 후보 또는 어느 허브에서 언급)입니다. 사용자가 하나를 고르면 진행합니다.

## 절차
1. my-kit:mcp-researcher 에이전트에게 검토 주제에 비추어 저장소의 구조, 주요 기능, 연동 방식, 인증과 보안 기능, 버전 전환 현황 조사를 맡깁니다. 요청에 다른 my-kit: 에이전트가 적혀 있으면 그 에이전트에게 맡깁니다.
2. 받은 결과를 아래 출력 형식 그대로 정리합니다. 형식의 항목 이름과 순서를 바꾸지 않습니다.
3. my-kit:evidence-reviewer 에이전트에게 초안 검토를 맡겨 PASS, WARN, FAIL을 받습니다. FAIL이면 지적을 고친 뒤 한 번 더 검토받습니다.
4. reports/ 폴더에 두 파일로 저장합니다. "조회일-저장소.md"는 아래 출력 형식, "조회일-저장소.html"은 아래 웹 리포트 형식입니다. 파일 이름의 저장소에서 '/'는 '_'로 바꿉니다. 같은 저장소의 지난 리포트가 있으면 3번 항목에서 비교합니다.

## 출력 형식
# (검토 주제) 도입 검토: (저장소) (조회일 YYYY-MM-DD)
1. 요약: 세 줄 이내. 첫 줄은 검토 주제에 대한 도입 권고(권장, 조건부, 보류 중 하나)와 한 줄 근거
2. 핵심 표: 항목, 내용, 직전 리포트 대비, 출처. 항목은 주제 적합성, 목적과 범위, 주요 구조, 연동 방식, 인증과 보안 기능, 버전 전환 현황, 운영 시 고려사항. 해당하지 않는 항목은 해당 없음으로 적습니다.
3. 눈에 띄는 변화와 이유: 버전 전환, 구조 개편, 주요 API 변경과 그 이유
4. 확인하지 못한 것: 자료로 확인하지 못한 항목(위키가 생성되거나 갱신된 시점, 라이선스, 유지보수 활동, 보안 취약점 이력 등 포함)
5. 검토 결과: PASS, WARN, FAIL 중 하나와 한 줄 이유

## 웹 리포트 형식 (HTML)
- 비개발자가 보는 한 장짜리 보고서입니다. 외부 라이브러리나 CDN 없이 HTML 파일 하나로 만듭니다.
- 순서: 제목(검토 주제, 저장소)과 조회일, 자료 출처 / 세 줄 요약 박스(도입 권고 강조) / 요약 카드 3~4개 / 핵심 표(위 2번과 같은 항목) / 확인하지 못한 것 / 검토 결과
- 차트는 숫자 자료가 있을 때만 인라인 SVG로 그립니다. 숫자를 지어내지 않습니다. 인쇄하거나 PDF로 저장해도 한 장에 들어가게 합니다.

## 지키는 것
- 리포트 내용은 이 plugin의 에이전트와 MCP 도구가 준 자료만 씁니다. 저장소 후보의 지식 제안만 예외이며, 후보도 MCP로 확인된 것만 씁니다.
- 출처에는 자료 이름과 조회일을 적습니다. DeepWiki 자료는 AI가 생성한 위키라는 점을 출처에 밝힙니다.
- 개인 식별 정보(이름, 주민번호, 카드, 계좌, 휴대폰, customer_id, 건물명과 번지)와 키, 토큰 값은 쓰지 않습니다.
