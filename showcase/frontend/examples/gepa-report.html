  1. 조건부프롬프트·코드 등 텍스트를 LLM 반성과 파레토 선택으로 최적화하며 DSPy와는 같은 엔진으로 연동되지만(FAQ 설명 기준), 평가자(evaluator) 코드 격리와 키 관리 기능이 확인되지 않아 통제 조건이 필요합니다.
  2. 연동은 dspy.GEPA, LiteLLM 기반 LLM 호출로 단순하고, README 기준 어댑터(DSPy, RAG, MCP, LangChain 등)가 다양합니다.
  3. 도입 시 예산 상한, 실행 폴더(run_dir), seed 설정이 필요하고, 평가 피드백이 외부 LLM에 그대로 전달되므로 민감정보를 넣지 않는 사내 규칙이 전제입니다.

확인하지 못한 것

  • 위키의 생성·갱신 시점과 기준 커밋
  • 유지보수 활동(커밋 빈도, 이슈 대응, 릴리스 주기)
  • 보안 취약점 이력(CVE, 보안 공지)
  • 릴리스별 버전 이력, CHANGELOG, 마이그레이션 노트, API 변경과 버전의 대응
  • 라이선스: MIT라는 위키 답변만 있고 원 저장소·의존성 라이선스 미확인
  • 설치 방식(pip install gepa)과 선택 패키지(extras) 재대조
  • optimize() 진입점의 병렬 기본값(위키 설명 상충)
  • Claude 기반 엔진(autoresearch 등)의 인증 요구사항
  • 평가 피드백 취급에 대한 공식 문서 경고 여부
  • LLM 전송 프롬프트 전체 구성, 제공자의 데이터 보관·학습 정책
  • execute_code 유틸리티의 실제 격리 수준
  • 위키 8.9 비용 추적, 8.10, 8.11 병렬 제안, 7.6 운영 사례, 11 타 방법 비교 본문
  • AI 생성 자료이므로 도입 결정 전 소스 코드·공식 문서로 교차 검증 필요
