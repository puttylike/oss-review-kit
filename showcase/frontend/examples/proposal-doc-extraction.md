# 사내 문서 추출 프롬프트 자동 최적화 도입 기획안

작성 기준일 2026-11-17 · 근거: `reports/2026-11-17-gepa-ai_gepa.md`(이하 "리포트")와 추가 조사(DeepWiki gepa-ai/gepa, AI 생성 위키, 조회일 2026-11-17, 이하 "추가 조사"). 근거 번호 [E1]~[E14]는 6절 근거 표를 가리킵니다.

## 1. 배경과 문제
- (가정, 사내 확인 필요) 사내 문서에서 필드를 뽑는 추출 프롬프트를 사람이 고쳐 가며 맞추고 있다면, 문서 유형이 늘거나 모델이 바뀔 때마다 같은 작업을 반복하게 됩니다.
- gepa-ai/gepa는 프롬프트를 포함한 평가 가능한 텍스트를, 평가 결과의 피드백을 LLM이 반성해 고치는 방식으로 자동 최적화합니다 [E1]. 리포트의 도입 권고는 **조건부**입니다 [E2].
- 추출 과제 적용 사례가 위키에 정리되어 있습니다. DSPy 공식 튜토리얼 "GEPA for Structured Information Extraction"이 있고 [E3], 연락처 추출 정확도 86%→97%, Dropbox Dash 사례의 잘못된 JSON 출력 비율 40%→3% 미만 같은 수치가 소개되어 있습니다 [E4]. 다만 이 수치는 외부 자료에 대한 위키의 요약이며 원문은 확인하지 못했습니다.

## 2. 대상 고객 또는 사용자
- 1차 사용자: 사내 문서 추출 파이프라인을 운영하는 데이터·AI 개발 담당자. 정답 필드가 있는 평가 데이터와 평가 함수를 만들 수 있는 조직이 전제입니다 [E5].
- 2차 수혜자: 추출 결과를 쓰는 현업 부서. 프롬프트 수정 요청 없이 품질이 개선되는지는 파일럿으로 검증할 가설입니다(사내 조건 효과 근거 없음) [E14].

## 3. 제안 내용
**구조**
1. **평가 세트 준비**: 문서 유형별로 정답 필드가 있는 학습·검증 세트를 만듭니다. 개인정보는 비식별 처리한 문서만 씁니다.
2. **평가 함수(evaluator)**: 필드별로 정답과 출력을 비교해 점수와 텍스트 피드백(예: 어느 필드가 틀렸는지)을 돌려줍니다. GEPA는 `(score, side_info)` 형태나 DSPy의 `score`+`feedback` 형태 피드백을 받을 수 있습니다 [E5].
3. **최적화 실행**: `optimize_anything` 또는 DSPy를 쓰는 경우 `dspy.GEPA`로 실행합니다 [E6]. GEPA는 종료 조건(평가 횟수 또는 반성 비용 상한)이 최소 하나 있어야 실행되며, 이 기획안은 재현성 관리를 위해 run_dir과 seed도 명시 지정을 사내 규칙으로 둡니다(seed 기본값은 0) [E7].
4. **모델 연결**: 사내 호스팅 모델을 LiteLLM 모델 ID(api_base 지정)나 사용자 정의 callable로 연결해, 문서 내용이 외부로 나가지 않는 구성을 우선 검토합니다 [E8]. ComBEE 반성 LM을 callable로 연결하는 경우 반성 비용 상한을 쓸 수 없으므로 평가 횟수 상한으로 예산을 통제합니다 [E8].
5. **결과 반영**: 최적 프롬프트는 `result.best_candidate`로 받고, `to_dict()` JSON으로 저장해 버전 관리한 뒤 운영 파이프라인에 반영합니다 [E9].
6. **추적**: W&B 또는 MLflow로 실행 기록을 남깁니다 [E10].

**단계**
- 1단계(파일럿): 문서 유형 1~2개, 사내 호스팅 모델, 비식별 데이터로 현재 수작업 프롬프트와 비교합니다.
- 2단계(확대): 파일럿 결과와 5절 보안 조건 충족 여부를 보고 문서 유형을 늘립니다.

## 4. 기대 효과와 측정 지표
- **추출 품질**: 필드별 정확도와 문서 단위 완전 일치율을 수작업 프롬프트와 비교합니다. 목표 수치는 파일럿 기준선을 잰 뒤 정합니다(근거 자료에 사내 조건의 수치가 없음) [E14].
- **출력 형식 안정성**: 잘못된 JSON 출력 비율. 외부 사례에서 개선 사례가 보고되었습니다 [E4].
- **비용**: 최적화 1회당 평가 횟수와 반성 비용. ComBEE 반성 LM에 callable을 쓰면 토큰은 추정치이고 비용은 0.0으로 보고되므로, 그 경우 사내 모델 비용은 별도로 집계합니다 [E8].
- **작업 시간**: 문서 유형 하나의 프롬프트 개선에 드는 담당자 작업 시간.

## 5. 리스크와 유의사항
- **개인정보·데이터 전송**: 평가 피드백(info)은 제안용 LLM에 그대로 전달됩니다 [E11]. 외부 LLM을 쓰면 문서 내용과 피드백이 외부로 나가므로, 비식별 데이터 사용과 사내 호스팅 모델 우선을 원칙으로 합니다. LLM 제공자의 데이터 보관·학습 정책은 확인되지 않았습니다 [E14].
- **격리**: 샌드박스는 Claude 서브프로세스에만 적용되고 평가 코드와 GEPA 프로세스 전체는 격리되지 않습니다 [E11]. 평가 함수는 검토된 코드만 쓰고, 별도 격리 환경에서 실행합니다.
- **키 관리**: 키 보관소·마스킹 기능이 확인되지 않아 [E11], 사내 비밀 관리 체계로 환경변수를 주입합니다.
- **비용 폭주**: 종료 조건이 없으면 실행할 수 없고, 평가 횟수 기본값 100은 선택 집합이 크면 낮을 수 있습니다(선택 집합 크기의 약 15~20배 권장) [E7]. ComBEE 반성 LM을 callable로 연결하면 반성 비용 상한(`max_reflection_cost`)이 거부되고 비용이 0.0으로 보고되어 비용 기준 통제가 되지 않습니다 [E8]. 평가 횟수 상한과 사내 모델 사용량 집계를 승인 절차에 넣습니다.
- **데이터의 한계**: 근거는 모두 AI 생성 위키이고, 외부 사례 수치는 원문을 확인하지 못했습니다. 한국어 사내 문서와 사내 호스팅 모델 조건의 효과 근거는 없습니다 [E14].
- **재현성**: seed를 지정해도 외부 모델 결과가 같다는 보장은 없습니다 [E7].
- **오픈소스 라이선스와 유지보수**: 라이선스는 MIT라는 위키 답변만 있고 원 저장소로 교차 확인하지 못했습니다. 버전은 0.1.4로 1.0 이전이며, 유지보수 활동과 보안 취약점 이력은 확인되지 않았습니다 [E12][E13]. 도입 전에 법무 검토와 원 저장소 확인이 필요합니다.
